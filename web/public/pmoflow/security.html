Security and data handling

Your data and keys never leave your tenant.

PMOFlow is a hosted display layer. Your process and project records live in your own Microsoft tenant. This page states what is in place today, how it works in your tenant, and what is still planned.

The display-layer model

  • Your records stay with you. Process and project records live in your own Azure tenant, behind an API that runs in your subscription under your managed identity. PMOFlow draws the screens.
  • The browser never holds tokens for Microsoft Graph, SharePoint or your source systems. The only scope it requests is your own PMOFlow API. SharePoint access uses per-site permissions (Sites.Selected), never tenant-wide.
  • Integration keys stay in your Key Vault. Jira, Azure DevOps and GitHub credentials are read only by your managed identity. PMOFlow never stores your tokens.
  • Sync instructions are signed and expire. Each one is signed with a per-project rotating secret, carries a one-time value, expires after 5 minutes and is refused if replayed.
  • Kill switch. Disabling the PMOFlow enterprise app in Microsoft Entra ID stops everything.
  • Logs go to your own Log Analytics or Sentinel, with detection rules that ship with the product.
  • In place No third-party scripts in the app: no analytics and no tag managers. These product pages load none either.

Access to real data: one project, time-boxed

  • In place Access is granted for testing one project. The owner of the information approves it, it expires, and it closes automatically at launch. The live demo shows this.
  • In place Sample checks return statistics only (lengths, blanks, characters), never the values. No values are kept.
  • In place A step-up check at sensitive moments: approvals, go-live and access grants. In your tenant this is Microsoft Entra Conditional Access authentication context. (The demo accepts any 6 digits.)

Sign-in with Microsoft Entra ID

  • Single sign-on with Microsoft Entra ID on the Business and Enterprise plans.
  • Your Conditional Access rules apply, including compliant devices, and sessions are short: the 24-hour single-page-app refresh-token limit is inherited from your tenant.
  • Planned SCIM user provisioning on the Enterprise plan.

Roles and separation of duties

  • Four roles: Admin, Editor, Approver and Viewer. Approvers and viewers are free seats.
  • In place Separate approvers. Nobody approves a team’s part if they recorded any test result for it or own steps in it. The project manager and the launch owner don’t approve teams’ parts.
  • In place Passing tests. People pass only tests assigned to them or to no one, and a test linked to an open problem can’t pass until it is fixed.
  • In place Two people for launch overrides. Launching outside the launch window, or with launch-day tasks still open, needs the project manager and a sponsor or approver, each with the extra sign-in check.
  • In place Department changes. Naming the first approver of a department that has none takes one Admin. With two or more Admins, moving someone between departments or changing a department’s existing approvers is proposed by one Admin and confirmed by another with the extra sign-in check; the person it moves can’t confirm it, and nothing changes until then. In a workspace with one Admin, those changes apply at once and History says so. Each membership and approver keeps the date it started.
  • In place Recent moves. Someone moved into a department, or made an approver, after its testing or approval started can’t pass its tests or approve it.
  • In place No Admin exemption. The server checks every rule above, for Admins too.
  • In place Each department approves only its own part of a process change.

Audit

  • In place Every change is recorded in history: who, what and when.
  • In place History text is written by the server from the actual change. For each saved change the server compares the record before and after and writes the sentence itself, field by field (for example: due “2026-12-08” → “2027-01-07”). Anything the person typed is kept only as a quoted note after it, so a change can’t be logged as something else. Entries saved before this rule keep the wording they had, and the Admin history marks them as older entries.
  • In place Audit export as CSV or JSON. Each entry carries a SHA-256 fingerprint of itself and the entry before it.
  • In place Signed exports. A full JSON export carries a signed head: the number of entries and the last fingerprint, signed (HMAC-SHA256) with a key held by the PMOFlow service. Checking the file in Admin catches an edited entry, entries removed from the end, and fingerprints recomputed after export.
  • In place Checkpoints. Each export records the current head, so a later change to history up to that point shows up as broken.
  • What this does not prove. Fingerprints are worked out from the stored history when you view or export it, not as each change is saved. The signature shows a file came unchanged from the PMOFlow service; it is not an independent notary.

Encryption

  • In transit: PMOFlow is served over HTTPS only.
  • At rest, in your tenant: your records stay in your own Microsoft 365 and Azure services and inherit their encryption and your key choices.
  • At rest, on our side: the hosted layer runs on Azure, where Azure Storage encrypts stored data by default.
  • Sync instructions are signed (HMAC) with a per-project rotating secret.

Hosting on Azure

  • The display layer is hosted on Microsoft Azure. If it is down, the screens are down; your data is unaffected.
  • No standing access to your Azure. Onboarding is your admin running our template in your subscription.
  • How we build it: multi-factor sign-in with hardware keys, protected branches, pinned dependencies and a software bill of materials (SBOM).
  • In place The live demo holds only fictional data, keeps each visitor’s sandbox for 30 days, and stores visitor IP addresses only as a salted hash.

What the Team plan needs from IT

  • A one-time setup in your Azure subscription. Your admin runs our template, which sets up the API your records live behind, under your own managed identity. We get no standing access to your Azure.
  • No relay, no tool keys. The relay is a small Azure Function in your subscription, and it is only needed when you connect Jira or Azure DevOps or send Teams and Outlook notifications. Those are Business-plan features, so Team runs without it.
  • Nothing installed on people’s computers. PMOFlow runs in the browser.
  • On Business you add sign-in with Microsoft Entra ID and, if you want them, the relay for Jira, Azure DevOps, Teams and Outlook, with its keys in your Key Vault.

If PMOFlow goes away

  • Your records stay in your tenant. They live in your own Azure subscription, not with us. If you leave, or we do, you keep them and lose the screens.
  • In place Export at any time: process maps as BPMN 2.0 files other tools open, work items and the portfolio as CSV, and the full change history as CSV or JSON.
  • If our hosting is down, the screens are down. Your data is unaffected.
  • On request Source code escrow for Enterprise. PMOFlow's source code and build instructions are deposited with an independent escrow agent and kept up to date. If PMOFlow stops trading or stops supporting the product, the agent releases them to you so you can keep running it. The escrow agent's fee is paid by the customer who asks for it.

AI data handling

  • In place AI runs on Azure OpenAI and is given only the facts it needs, such as task names, dates and status, to write a status summary or suggest a plan.
  • In place Sample data and sample statistics are never sent to the AI.
  • In place The AI is told to use only the facts supplied and never to invent people, dates, numbers or systems. Every AI feature has a rules-based fallback that works with AI turned off, and each result says which one produced it.

Roadmap: planned, not yet done

PMOFlow does not hold any security certification today. These items are planned:

  • Target Q1 2027 Third-party penetration test, then annually. The summary letter is shared with customers on request.
  • Target Q3 2027 SOC 2 Type I, followed by SOC 2 Type II. Not yet obtained.
  • Planned Customer-approved, signed releases with a verifying loader and a public transparency log, for regulated buyers.
  • Planned SCIM provisioning on the Enterprise plan.

Known limits, stated plainly

  • One of your admins could be tricked into approving a malicious release. Signed releases (planned) address this.
  • A bug in our code can only act within the limits of the API in your tenant.
  • Browser sign-in tokens are not yet bound to a device. This is a platform limitation.
  • If our hosting is down, the display layer is down. Your data is unaffected.
